# `dataviz/llm/` — the ◆ AI assistant

LLM providers and the assistant features built on them. Routes: `server/routes/llm.py` (`/api/llm/*`), `server/routes/agent.py`
(`/api/llm/agent/*`, the ◆ agents), `server/routes/sessions.py` (`/api/llm/sessions*`).
Nothing here runs unless a provider is connected (saved, active, last Test connection passed) and the feature's
switch is on (all off by default).

| File | What it does |
|---|---|
| `store.py` | `LLMStore`, **per user** in PostgreSQL: `app.llm_providers` (private to their owner; API key Fernet-encrypted and write-only; `env:NAME` keys admin-only, never resolved for a non-admin) + `app.llm_user_config` (the active one, feature switches, token budget). Every method takes the acting user (default: the signed-in one); `state()` is what the page may show. |
| `providers.py` | Raw httpx clients (no SDKs) for `openai`, `openai_compat`, `anthropic`, `gemini` behind one message format `[{role, parts: [{text} / {jpeg, cache?} / {wav}]}]`: `chat_stream()` (SSE → deltas + usage), `complete()`, `complete_json()` (fences stripped, one retry with the parse error), `list_models()`, `test()`. Errors are `LLMError(msg, status)`; the key never appears in a message. |
| `budget.py` | Token estimates (text ≈ 3.5 chars/token; per-provider image formulas) and `fit()`: older images → `[image omitted]`, oldest turns dropped, context images downscaled / dropped, else 400. The limit of a request is `effective(setting, provider)`: the Settings budget (a number, or `auto` = the default) kept under `ceiling()`, the model's context window less room for its answer (`providers.model_limits`: the card's Model context, else the provider's API (Gemini `inputTokenLimit`, Claude `max_input_tokens`, OpenRouter / vLLM / Groq / LM Studio / llama.cpp / Ollama fields), else `MODEL_CONTEXT`; asked once per model); 100k when the size is unknown. |
| `context.py` | Compact context: `dataset_summary` (text tables), `eval_summary` (via `routes/models.eval_overview`), `selection_mosaic` (≤ 24 crops in one numbered JPEG + legend), `image_mosaic`, class exemplar sheets (`state_exemplars`, `task_exemplars`, cached per task + annotation count), `prepare_image` (≤ 1024 px). |
| `providers.py` (tool calling) | `stream_tools(p, system, msgs, tools, think, native_web)`: the engine's streamed step for all 4 kinds (text, thinking with signatures, tool calls, native web search, why it stopped: `length` = cut off by the output limit, which the engine retries once with twice the room (`react.output_room`: a thinking OpenAI-style / local model also starts with THINK_OUT low 4k / medium 8k / high 16k, all under Admin › Settings `llm_think_output` and what the context window leaves); refused parameters dropped once and remembered per model). Below: the non-streamed form. |
| `providers.py` (non-streamed tools) | `complete_tools(p, system, msgs, tools)`: one non-streamed native tool-calling step → `{text, tool_calls: [{id, name, args, sig?}], usage}`. History parts `{tool_call: {id, name, args, sig?}}` (assistant) and `{tool_result: {id, name, content, is_error?}}` (a `tool` message) become OpenAI `tool_calls` + role `tool` messages, Anthropic `tool_use` / `tool_result` blocks (results open the user turn), Gemini `functionCall` (with its `thoughtSignature`) / `functionResponse`; Gemini schemas cut to its OpenAPI subset (`gemini_schema`). Arguments that are not a JSON object parse as `args: None`; a missing id is `''` (the agent assigns one). |
| `tools/` | One registry (`REGISTRY`), filled by every module of the folder: a new tool is a new `register(Tool(...))`. Each tool has a **domain** (`bucket`, `visual`, `data`, `web`, `common`, `control`, `plugin`) and a **risk** (`read` runs at once; `change` is confirmed in mode ask, run in mode auto; `danger` is always confirmed; `ui` is a page action (applied in auto, an Apply button in ask; `open_tab` / `navigate` always); `run` is a page action that starts work (a map, a model run, a scan): confirmed in ask, run in auto, the page reports how it ended (`engine/uiwait.py`, POST `/api/llm/agent/ui-result`) and a transient failure is retried twice; `control` is handled by the engine). `bucket.py`: the Bucket page tools (also `TOOLS`, the CLI and `.claude/skills/bucket/SKILL.md`; `job_status` reads a background job a tool started, and a result with `job_id` or a `job_status` gives the page a `job` event: the dock's job row); `control.py`: `ask_user`, `cannot_do`, `todo` (a page per step; saved on the chat as its plan, shown to later turns while a step is open), `submit_plan`; `skills.py`: `use_skill`, `read_docs`; `web.py`: `web_search`, `fetch_url`; `visual.py`: the visual agent's read tools, page actions and run actions (`set_projection`, `run_model`, `run_eval_all`, `run_scan`, `compute_stats`); `agents.py`: `delegate` (only when the user switched Sub-agents on, `budget.agents` in the config, `/agents`; never for a small model): 1-4 independent read-only tasks, each run by a copy of this page's specialist in its own short run (`engine/subrun.py`, which `consult` uses too; ≤ 8 steps, answer ≤ 2000 chars), in parallel threads (one after another for the visualizer), only the answers come back, their tokens count for the turn, an `agent` event per task; `nav.py`: `list_sessions` (+ bucket / path: the sessions of a Bucket folder), `consult` (the other page's specialist answers one question read-only on the server, ≤ 6 steps, only its answer comes back and its tokens count for the turn; no consult of a consult), `data_location` (visual only: the dataset's Bucket folder and its parents, `bucket/service.locate`), `navigate` (both agents: open another page; the turn ends and the dock of the new page opens the same chat and sends the goal as a continued message; refused when that page's assistant is off). `for_role(domains, mode)` is the set one agent gets; `prepare()` / `run()` take the user or the agent `Ctx`. |
| `engine/` | The agent engine every ◆ chat runs on. `react.py`: the ReAct loop (≤ 50 steps (Admin › Settings `llm_steps_max` / `llm_steps_medium` / `llm_steps_small`, `react.step_limits`; effort high takes the whole maximum) and ≤ 50 retries of a transient failure per run, a loop guard (3rd identical call nudged; the 5th compacts the work through `_compact_run(why='loop')`, blocks that call (its last result is returned instead) and goes on, at most `LOOP_RECOVER_MAX` 2 times; compact off stops as before), modes `ask` / `auto` / `plan`, effort `low` / `medium` / `high` (15 / 30 / 50 steps, thinking, a final check pass), the small-model profile (≤ 14B: 20 steps, ≤ 8 matching tools, temperature 0.1) and the medium one (15-40B, or a Model context of 40k or less: 25 steps, temperature ≤ 0.2, knowledge as an index, and tool groups (`tools.GROUPS`): the look-ups plus the groups the last messages name, `more_tools {group}` or a call to an unloaded tool loads another; about 6k tokens of prompt + tool definitions instead of 10-12k)); `confirm.py`: a change pauses the stream until `/api/llm/agent/confirm` (approve / reject / edited args), then the agent continues; `compact.py`: old tool results become stubs so 50 steps fit the budget; at a limit of one answer (the context past 90% of the budget after stubbing, or the last step) `react._compact_run` folds the answer's own steps (after `run.base_n`) into one progress summary (`templates/run_compact.md`, `summarize._call`) and goes on with a new batch of steps, at most `RUN_COMPACT_MAX` 3 times (event `run_compact` {n, phase ask/start/done/failed/declined, reason context/steps/loop}; chat pref `compact` auto | ask (the card, confirmed on `/api/llm/agent/confirm` a1) | off; a background worker never asks); `summarize.py`: chat compaction (past 80% of the budget or 40 unsummarised messages, and `/compact`): the older messages + their traces fold into one structured summary (`prompts/templates/compact.md`) stored on the chat, which the model reads in its system prompt instead of them; `roles.py`: the Data and Visual specialists behind the one chat (their domains, switch, scope text: the visual one has no data tool), the router input `page_of` and the short "Other pages" card (`other_pages`) each prompt carries instead of the other page's tools; `react.claim_chat` lets one run at a time answer a chat (409 for another tab); a call to another page's tool or skill gets "navigate there"; `planner.py`; `events.py`: the NDJSON protocol. |
| `prompting.py` + `prompts/` | The system prompt is built from Markdown, not code: `base.md` (every agent), `<role>/system.md`, `<role>/knowledge/*.md` (front matter `title`, `summary`, `core`, `high`: an index always, `core` topics inline from effort medium), `skills/<role|common>/<name>/SKILL.md`, `templates/` (modes, now). The user's own instructions (Settings › Prompts & Skills) are appended last and never replace the rules; their skills join the built-in ones. The prompt has a stable part (base with the installed zones' one-line intro, the role, knowledge, skills, `tools.risk_card` (which tools run at once and which wait: the names, arguments and descriptions already reach the model as native tool specs, so no second table), Other pages) and, after `prompting.DYNAMIC`, what changes per message (mode, a forced skill, Now + scope, the plan, the summary, the user's instructions). Claude gets them as two system blocks with the cache breakpoint on the stable one plus one on the last message (each loop step reads the earlier steps from the cache); OpenAI / Gemini get one text with the stable part first (`prompting.plain`). `bucket-agent.md` is the old agent's prompt. |
| `engine/bgtasks.py` + `tools/tasks.py` | **Background agents** (Sub-agents on, a saved chat, not a small model): the chat's assistant is the lead and stays free; `spawn_task {title, goal, mode?}` starts a worker (a run of this page's specialist in a server thread: no page / run action, no navigate, consult, delegate or spawn, so a sub-agent never starts a sub-agent; its mode is never looser than the chat's; it ends with `finish_task {summary, show?}`), `task_status` says what each did / does / has left with time, an estimate (only with a checklist) and tokens, `task_message` answers its question or approves its plan, `stop_task` stops it. A change inside a worker waits on a normal confirmation (30 min) that only the user decides (the Agents strip posts `/api/llm/agent/confirm`); no tool approves for them. Limits: the user's `budget.agents.max_running` 1-4 (default 2), 8 on the server (`llm_agents_max`), 8 queued per user. Routes: `GET /api/llm/agent/tasks?session_id=`, `POST .../tasks/{id}/stop`, `.../tasks/{id}/message {text | approve}`; chat `body.task_event = <id>` makes the server put the task's result (never the page's text) to the lead as the user message. In memory: a restart drops running agents. Prompt: `templates/lead.md`. |
| `web_guard.py` | Every outgoing web query / URL is checked on the server: level 1 public (no internal names), 2 technical (class / tag / format names allowed), 3 full (only secrets and "never" special words blocked; the provider's own search only here). Internal names come from the turn's tool results, buckets, classes, connections, the user; special words from Admin › Settings and the user's list. |
| `sessions.py` | Saved chats (`app.llm_sessions` / `llm_messages`). **One chat, every page**: chats are role `app` and continue on any page; each message keeps its `page` (`{role, screen, label, ...}`) and the history the model reads marks where the user moved (`react.history`). 20 per user (role `app` counts every chat; the one not opened longest is soft-deleted first, pinned ones never), delete = `deleted_at` (purged after `llm_chat_retention_days`, 730 by default, by a daily thread under an advisory lock), compacted traces, ILIKE search; `summary` / `summary_seq` (the compacted part: `context()` is the summary + the messages after it). A turn the page draws itself (the Visualizer's label check and auto-tag) is saved by `POST /api/llm/agent/<role>/note {session_id?, request, result}` as a user + an assistant message (`chat.record`), so a reload shows it and the model reads it. |
| `agent.py` | The OLD Bucket agent behind `/api/llm/bucket/chat` + `/api/llm/bucket/confirm` (≤ 8 steps, every change ends the turn as a plan): kept for that route and its tests; the ◆ chats run on `engine/` through `/api/llm/agent/*` (server/routes/agent.py). |
| `tasks.py` | Structured features, JSON answers validated server side: `label_check`, `nl_filter` (+ `clean_filter`, the `core/filter.js` `emptyFilter()` shape), `auto_tag_job` (a job writing `ai:<tag>` tags), `label_assist` (boxes converted from the provider's `box_format` to normalised x1y1x2y2), `voice` (whitelisted actions). |

## Zones

A specialist exists only when its zone is installed (`engine/roles.py` `Role.zone`, `roles.installed()`): the Other pages card, `navigate`, `consult` and skill hints follow it, and the card tells the model what this install lacks. A new specialist is a new `Role` plus its prompts folder.

## Token cost

One mosaic image instead of N crops; full images ≤ 1024 px; summaries as text tables; the exemplar sheet goes
first and is flagged for prompt caching (Anthropic `cache_control`; OpenAI / Gemini cache identical prefixes
automatically); `fit()` runs before every call and the chat reports the estimate (`meta.in_est`) and the provider's
usage (`done.usage`, billed over every step; our estimate when a server reports none). The context ring follows
`context {used, limit, exact}` events (after meta, after each step's tool results, and the provider's count once a
step answered); `done.ctx` is saved with the answer's usage so a reopened chat shows it.
